# Invite Mailer – первая рабочая версия

Проект предназначен для запуска в Portainer на отдельном Docker-сервере.

Он выполняет следующие действия:

1. После 08:30 подключается к почтовому ящику Zimbra по IMAP.
2. Находит последнее письмо от `1c-robot@` с вложением `Штатные сотрудники - Телефонный справочник2 (XLSX).xlsx`.
3. Скачивает вложение через `BODY.PEEK[]` и не меняет состояние письма.
4. Извлекает сотрудников из XLSX.
5. Берет email только из колонки `Физическое лицо.Адрес электронной почты`.
6. Колонка `Состояние` не используется.
7. СНИЛС используется только для формирования технического HMAC-идентификатора и не выводится в отчет.
8. Раз в неделю определяет, кому нужно отправить письмо.
9. Поддерживает разовые и периодические шаблоны.
10. Формирует внутренний HTML-отчет со статусами отправки и прохождения тестов.
11. При `INDIGO_ENABLED=true` получает результаты из PostgreSQL Indigo в режиме read-only и сохраняет локальный кеш.
12. Исключения e-mail → логин редактируются в административном разделе.

Актуальные инструкции по обновлению находятся в `README_INDIGO_UPDATE.md`.

## 1. Подготовка каталога

Распакуйте проект на Docker-сервер, например:

```bash
mkdir -p /opt/invite-mailer
cd /opt/invite-mailer
```

Скопируйте содержимое проекта в этот каталог.

При локальном запуске создайте `.env`:

```bash
cp .env.example .env
```

При запуске через Portainer те же переменные можно добавить в разделе **Environment variables**. Заполните параметры IMAP, SMTP, внутренний IP сервера и длинный случайный `WORKER_HASH_SECRET`.

Рабочая база, загруженные XLSX и HTML-отчет сохраняются вне контейнера в каталоге, заданном переменной `STORAGE_ROOT`. По умолчанию используется `/opt/invite-mailer-storage`.

В `config/config.yaml` замените домен `domain.ru` на фактический почтовый домен.

В `templates/intro_tests.html` замените ссылки и текст письма.

## 2. Развертывание через Portainer

В Portainer откройте:

`Stacks` → `Add stack` → `Web editor`

Вариант A – если Portainer умеет собирать стек из Git: разместите проект в Git и укажите репозиторий.

Вариант B – удобнее для первого теста: создайте стек через `docker-compose.yml`, а каталог проекта заранее разместите на сервере. Для сборки локального Dockerfile Portainer должен работать с этим каталогом как с Git-репозиторием или через функцию загрузки стека.

После запуска должны появиться контейнеры:

- `invite-mailer`
- `invite-mailer-report`

HTML-страница будет доступна по адресу:

```text
http://ВНУТРЕННИЙ_IP_СЕРВЕРА:8080/
```

nginx разрешает доступ только из частных подсетей.

## 3. Ручная проверка получения XLSX

Откройте консоль контейнера `invite-mailer` в Portainer и выполните:

```bash
python -m app.main fetch
```

Проверьте:

- в `data/archive` появился XLSX;
- создан `data/current.xlsx`;
- в `state/invite_mailer.sqlite` появились сотрудники;
- HTML-страница обновилась;
- исходное письмо не изменилось.

## 4. Тест без отправки писем

```bash
python -m app.main run --dry-run --skip-fetch
```

Команда покажет количество писем, которые были бы отправлены, но ничего не отправит и не запишет ложные успешные отправки.

## 5. Первая ручная рассылка

После отправки первого письма через группу рассылки сначала загрузите XLSX, затем отметьте всех актуальных сотрудников как уже уведомленных:

```bash
python -m app.main seed --templates intro_tests --sent-date 2026-07-13
```

Дата указывается в формате `YYYY-MM-DD`.

## 6. Ручной рабочий запуск

```bash
python -m app.main run
```

Команда загрузит свежий XLSX, отправит необходимые письма и обновит HTML-отчет.

## 7. Добавление периодического шаблона

Пример в `config/templates.yaml`:

```yaml
templates:
  - id: "antiterror"
    enabled: true
    name: "Антитеррор"
    subject: "Приглашение к прохождению тестирования"
    body_template: "/opt/invite-mailer/templates/antiterror.html"
    mode: "periodic"
    validity_days: 365
    departments:
      include:
        - "*"
      exclude: []
```

Для теста только по определенным подразделениям можно использовать шаблоны `fnmatch`:

```yaml
departments:
  include:
    - "*Бухгалтерия*"
    - "*Отдел закупок*"
  exclude: []
```

## 8. Нестандартные логины

По умолчанию логин получается из части e-mail до `@`.

Исключения редактируются на странице `/admin/logins/`. Прежние значения из `LOGIN_OVERRIDES_JSON` и `config/login_overrides.yaml` один раз переносятся в SQLite для обратной совместимости. После переноса дальнейшие изменения выполняются через административный раздел.

## 9. Важные ограничения первой версии

- Структура XLSX проверена по предоставленному изображению, но не по реальному файлу.
- Названия колонок должны совпадать с настройками.
- Подразделение определяется по последней строке-группе перед сотрудником.
- Перед реальной рассылкой обязательно выполнить ручной `fetch` и `run --dry-run`.
- Перед включением Indigo необходимо задать реквизиты read-only подключения в Portainer и выполнить `python -m app.main indigo-sync`.

## Версия 2.1.0 – повторные напоминания

Добавлен рабочий ежедневный цикл повторных напоминаний. После успешной первичной
рассылки система ожидает заданный в общих настройках интервал и отправляет
напоминания работникам, которые еще не завершили тест. Ручная первичная рассылка,
добавленная командой `seed`, также участвует в этом цикле.

После исчерпания максимального количества напоминаний и окончания очередного
интервала работник получает статус «Игнорирует прохождение». Уведомление ставится
в надежную очередь для контролирующих соответствующего теста. Если письмо не
доставлено или контролирующий пока не назначен, запись остается в очереди. После
добавления или изменения контролирующего накопленные уведомления по назначенным
ему тестам обрабатываются сразу.

Добавлена команда ручного запуска:

```bash
python -m app.main reminders
python -m app.main reminders --dry-run
```

В режиме планировщика цикл запускается ежедневно после получения свежего XLSX.
Подробные результаты записываются в журнал уведомлений. Старые записи журнала
удаляются автоматически по сроку хранения из общих настроек.

## Версия 2.1.1 – уточнение статистики и интерфейса

- Показатель «Ожидают» в статистике выбранного теста больше не учитывает работников без e-mail.
- Работники со статусом «Игнорирует прохождение» по-прежнему учитываются в числе ожидающих, пока присутствуют в актуальном файле 1С.
- Общий виджет «Без e-mail» при ненулевом значении выделяется бледным предупреждающим фоном и тонкой рамкой.
- Кнопки в шапках раздела настроек приведены к единому стилю и расположению, используемому в отчете.


## Версия 2.1.2 – единый подсчет участников

- В счетчике «Участники» выбранного теста не учитываются активные работники без адреса электронной почты.
- Число участников, указанное рядом с названием теста в списке выбора, рассчитывается по тому же правилу.
- Работники без e-mail остаются в таблице отчета и учитываются в отдельном общем показателе «Без e-mail».
- Статус «Игнорирует прохождение» не исключает работника из числа участников.
